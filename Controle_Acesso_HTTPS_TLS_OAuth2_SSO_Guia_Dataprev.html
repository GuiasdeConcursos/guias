1. Fundamentos: AAA, Autenticação x Autorização

O modelo clássico de segurança de acesso é descrito pela sigla AAA:

ComponentePergunta que respondeExemplos
Authentication (Autenticação)"Quem é você?"Login/senha, certificado digital, biometria, MFA
Authorization (Autorização)"O que você pode fazer?"Permissões, papéis (roles), políticas de acesso
Accounting/Auditing (Registro/Auditoria)"O que você fez?"Logs, trilhas de auditoria, non-repudiation
⚠ PEGADINHA: Autenticação ≠ Autorização. Autenticação prova identidade (ex.: login bem-sucedido); autorização decide o que essa identidade pode acessar. É comum a banca trocar os dois termos, ou afirmar que "o OAuth 2.0 é um protocolo de autenticação" (FALSO — OAuth 2.0 é um framework de autorização).

1.1 Fatores de autenticação e MFA

  • Algo que você sabe (knowledge) — senha, PIN, pergunta de segurança.
  • Algo que você tem (possession) — token físico, smart card, celular (OTP/app autenticador).
  • Algo que você é (inherence) — biometria (digital, face, íris).
  • (fatores complementares às vezes citados: "algo que você faz" — comportamento — e "onde você está" — localização/contexto).

MFA (Multi-Factor Authentication) exige 2 ou mais fatores de categorias diferentes. Duas senhas não configuram MFA, pois pertencem à mesma categoria ("algo que você sabe").

1.2 Princípios de controle de acesso

  • Princípio do menor privilégio (least privilege) — conceder apenas o acesso mínimo necessário para a função.
  • Need-to-know — acesso apenas à informação estritamente necessária.
  • Segregação de funções (Segregation/Separation of Duties – SoD) — dividir tarefas críticas entre pessoas diferentes para evitar fraude/erro.
  • Defesa em profundidade (defense in depth) — múltiplas camadas de controle, não dependência de um único mecanismo.

2. Modelos de Controle de Acesso

ModeloComo funcionaQuem decide o acesso
DAC — Discretionary Access ControlO proprietário do recurso define quem acessa, geralmente via ACL (Access Control List)O dono do recurso (discricionário)
MAC — Mandatory Access ControlAcesso definido por rótulos/classificações de sigilo impostos centralmente pelo sistema (ex.: "confidencial", "secreto")Sistema/política central — usuário não pode alterar
RBAC — Role-Based Access ControlPermissões atribuídas a papéis (roles); usuários recebem papéisAdministrador, via definição de papéis
ABAC — Attribute-Based Access ControlRegras/políticas avaliam atributos do usuário, do recurso, da ação e do ambiente (ex.: hora do dia, localização)Motor de políticas (policy engine), dinâmico
📌 MAC é o modelo mais rígido/centralizado (típico de ambientes militares/governamentais); DAC é o mais flexível (típico de sistemas de arquivos comuns, ex.: permissões do Windows/Linux); RBAC é o mais comum em ambientes corporativos; ABAC é o mais granular e dinâmico (usado em Zero Trust).

2.1 Modelos formais associados ao MAC

  • Bell-LaPadula — foca CONFIDENCIALIDADE. Regras: "no read up" (não pode ler nível acima) e "no write down" (não pode escrever em nível abaixo).
  • Biba — foca INTEGRIDADE. Regras invertidas: "no write up" e "no read down".
⚠ PEGADINHA: Bell-LaPadula (confidencialidade) e Biba (integridade) têm regras EXATAMENTE opostas entre si. A banca troca as regras de um modelo pelo outro — decore que Bell-LaPadula começa com "B" de "blindar leitura de cima" (no read up).

3. HTTPS

HTTPS (HTTP Secure) é o protocolo HTTP transmitido sobre uma camada de segurança TLS (Transport Layer Security), garantindo três propriedades:

  • Confidencialidade — dados cifrados em trânsito, ilegíveis para interceptadores.
  • Integridade — detecção de qualquer alteração dos dados no meio do caminho (MAC/AEAD).
  • Autenticação — o cliente verifica a identidade do servidor via certificado digital (e, opcionalmente, o servidor verifica o cliente — mutual TLS/mTLS).
ItemHTTPHTTPS
Porta padrão80443
Camada de segurançaNenhumaTLS (antigamente SSL)
Dados em trânsitoTexto claro (plaintext)Cifrados
📌 HSTS (HTTP Strict Transport Security) é um cabeçalho de resposta que força o navegador a só se comunicar via HTTPS com aquele domínio pelo tempo definido, mitigando ataques de downgrade (ex.: SSL stripping).

3.1 Certificados digitais e PKI

  • Certificados são emitidos por uma Autoridade Certificadora (CA – Certificate Authority) dentro de uma PKI (Public Key Infrastructure).
  • DV (Domain Validated) — valida apenas a posse do domínio (mais simples/rápido).
  • OV (Organization Validated) — valida também dados da organização.
  • EV (Extended Validation) — validação mais rigorosa da identidade jurídica da organização.
  • Cadeia de confiança: Root CA → CA(s) intermediária(s) → Certificado do servidor (folha).

4. SSL/TLS

SSL (Secure Sockets Layer) foi criado pela Netscape nos anos 1990. Todas as versões do SSL estão hoje obsoletas e desaconselhadas (SSL 3.0 foi formalmente depreciado pela RFC 7568, de 2015, devido à vulnerabilidade POODLE). O sucessor é o TLS (Transport Layer Security), padronizado pela IETF.

VersãoAnoSituação
SSL 2.01995Obsoleto/inseguro
SSL 3.01996Depreciado (RFC 7568) — vulnerável ao POODLE
TLS 1.01999Obsoleto (essencialmente "SSL 3.1")
TLS 1.12006Obsoleto
TLS 1.22008Ainda amplamente usado
TLS 1.32018 (RFC 8446)Atual — mais rápido e mais seguro
⚠ PEGADINHA: Na linguagem popular ainda se fala em "certificado SSL", mas tecnicamente as conexões HTTPS modernas usam TLS, não SSL. Afirmar que "o HTTPS usa o protocolo SSL" é impreciso/desatualizado para fins de prova técnica — o termo correto atual é TLS.

4.1 Criptografia híbrida no TLS

O TLS combina os dois mundos da criptografia:

  • Assimétrica (ex.: RSA, ECDHE/Diffie-Hellman) — usada na fase de handshake, para autenticação do servidor e troca/acordo da chave de sessão.
  • Simétrica (ex.: AES) — usada para cifrar o volume de dados da sessão (muito mais rápida que a assimétrica).

4.2 Handshake TLS 1.2 x TLS 1.3

TLS 1.2 (2 RTT — duas idas e voltas):
  1. ClientHello (cifras suportadas, número aleatório)
  2. ServerHello + Certificate + ServerKeyExchange + ServerHelloDone
  3. ClientKeyExchange + ChangeCipherSpec + Finished
  4. ChangeCipherSpec + Finished (servidor) → início dos dados cifrados
TLS 1.3 (1 RTT — uma ida e volta; e 0-RTT em retomada de sessão):
  1. ClientHello já inclui o "key share" (chave para Diffie-Hellman efêmero)
  2. ServerHello + key share + Certificate + Finished (já cifrados após o key share)
  3. Cliente confirma com Finished → início imediato dos dados de aplicação
📌 Principais avanços do TLS 1.3 em relação ao TLS 1.2:
  • Handshake reduzido de 2 RTT para 1 RTT (mais rápido); suporte a 0-RTT na retomada de sessão.
  • Eliminação de algoritmos fracos/obsoletos (RC4, MD5, SHA-1 no handshake, cifras de bloco CBC problemáticas).
  • Removida a troca de chaves RSA estática — agora o forward secrecy (sigilo futuro/perfeito) é obrigatório via Diffie-Hellman efêmero (ECDHE), impedindo que a captura futura da chave privada do servidor descriptografe tráfego passado.
  • Conjuntos de cifras (cipher suites) simplificados.
⚠ PEGADINHA: "Forward secrecy" (sigilo perfeito) significa que, mesmo que a chave privada do servidor seja comprometida no futuro, as sessões TLS passadas continuam protegidas — porque cada sessão usa uma chave efêmera diferente (Diffie-Hellman), nunca a chave privada de longo prazo diretamente para cifrar o tráfego.

5. OAuth 2.0

O OAuth 2.0 (RFC 6749) é um framework de autorização (não de autenticação) que permite que uma aplicação obtenha acesso limitado a recursos de um usuário em outro serviço, sem que o usuário precise compartilhar sua senha com a aplicação.

5.1 Papéis (Roles)

PapelFunção
Resource OwnerO usuário dono dos dados/recursos
ClientA aplicação que quer acessar o recurso em nome do usuário
Authorization ServerServidor que autentica o usuário e emite os tokens
Resource ServerServidor de API que hospeda os recursos protegidos e valida o token

5.2 Principais grant types (fluxos)

Grant typeUso típico
Authorization CodeFluxo padrão para aplicações web com back-end confiável; troca um "código" por um token via chamada servidor-a-servidor
Authorization Code + PKCERecomendado para SPAs (aplicações de página única) e apps mobile, que não conseguem guardar segredo com segurança
Client CredentialsComunicação máquina-a-máquina (M2M), sem usuário envolvido
Device CodeDispositivos sem navegador/teclado completo (ex.: smart TVs) — usuário autoriza em outro dispositivo
Refresh TokenUsado para obter um novo access token sem novo login, quando o anterior expira
Implicit (obsoleto)Antigo fluxo para SPAs, hoje desaconselhado em favor de Authorization Code + PKCE
Resource Owner Password Credentials (legado)Usuário fornece login/senha diretamente ao client — uso desaconselhado

5.3 Tokens

  • Access Token — token de curta duração usado para acessar o recurso protegido (tipicamente um "bearer token").
  • Refresh Token — token de longa duração, usado apenas para obter um novo access token, sem novo login do usuário.
  • Scope — define o conjunto de permissões que o token concede.
⚠ PEGADINHA: OAuth 2.0 NÃO é um protocolo de autenticação — ele delega AUTORIZAÇÃO de acesso a recursos. Usar OAuth 2.0 puro para "logar" um usuário (sem OpenID Connect) é considerado uma prática incorreta/insegura, pois o Access Token não garante informações confiáveis de identidade.

6. OpenID Connect (OIDC) — a camada de identidade sobre o OAuth 2.0

OpenID Connect é uma camada de autenticação construída sobre o OAuth 2.0. Ele resolve exatamente a limitação citada acima, introduzindo o conceito de identidade verificável.

  • Adiciona o ID Token, um token no formato JWT (JSON Web Token) contendo "claims" (afirmações) sobre a identidade do usuário autenticado (ex.: nome, e-mail, horário de autenticação).
  • Um JWT tem 3 partes separadas por ponto: header.payload.signature, codificadas em Base64URL.
  • Adiciona também o endpoint UserInfo, para consultar dados adicionais do usuário.
📌 Resumo da relação: OAuth 2.0 = autorização (o que a app pode acessar) → OpenID Connect = autenticação (quem é o usuário), construída como uma extensão do próprio OAuth 2.0.

7. SSO (Single Sign-On) e SAML

SSO é o mecanismo que permite ao usuário autenticar-se uma única vez e obter acesso a múltiplos sistemas/aplicações independentes, sem precisar reinserir credenciais em cada um.

7.1 Principais protocolos usados para implementar SSO

ProtocoloFormatoUso típico
SAML 2.0 (Security Assertion Markup Language)XMLSSO corporativo/empresarial clássico, integração entre organizações (federação)
OAuth 2.0 / OpenID ConnectJSON / JWTSSO moderno em aplicações web e mobile
KerberosTickets bináriosSSO dentro de uma rede corporativa/Active Directory (KDC, TGT, tickets de serviço)

7.2 Fluxo típico do SAML

  1. Usuário tenta acessar o Service Provider (SP – a aplicação).
  2. SP redireciona o usuário ao Identity Provider (IdP).
  3. Usuário se autentica no IdP (login único).
  4. IdP gera uma SAML Assertion (documento XML assinado digitalmente) e a envia de volta ao navegador do usuário.
  5. O navegador entrega a Assertion ao SP (tipicamente via POST automático de um formulário).
  6. SP valida a assinatura da Assertion e concede acesso.

7.3 Federação de identidades

A federação é a relação de confiança estabelecida entre um IdP e um ou mais SPs (podendo cruzar fronteiras organizacionais), permitindo que a identidade validada em um domínio seja aceita em outro, sem duplicar cadastros de usuário.

⚠ PEGADINHA: SSO é um CONCEITO (autenticar uma vez, acessar vários sistemas); SAML, OAuth2/OIDC e Kerberos são PROTOCOLOS/mecanismos que podem implementar esse conceito. A banca pode tentar fazer você confundir "SSO" com "SAML" como se fossem sinônimos — SAML é apenas um dos meios de se obter SSO.

11. Pegadinhas Consolidadas (revisão de véspera)

  • OAuth 2.0 ≠ autenticação. É um framework de AUTORIZAÇÃO. Quem autentica é o OpenID Connect (camada construída sobre o OAuth2).
  • "Certificado SSL" é termo popular desatualizado — tecnicamente hoje é TLS; SSL está obsoleto/depreciado.
  • TLS 1.3 reduziu o handshake de 2 RTT (TLS 1.2) para 1 RTT, e eliminou a troca de chaves RSA estática, tornando o forward secrecy obrigatório.
  • Bell-LaPadula (confidencialidade: no read up/no write down) e Biba (integridade: no write up/no read down) têm regras opostas — não troque um pelo outro.
  • DAC = dono do recurso decide (discricionário); MAC = sistema/política central decide (mandatório, rótulos de sigilo).
  • SSO é o conceito; SAML, OAuth2/OIDC e Kerberos são protocolos/mecanismos que o implementam — não são sinônimos.
  • SAML usa XML e "Assertions"; OAuth2/OIDC usam JSON e tokens (JWT no caso do OIDC).
  • Access Token (OAuth2) concede acesso a recursos; ID Token (OIDC) prova identidade — não confundir os dois tipos de token.
  • Refresh Token serve para renovar o Access Token sem novo login — não concede acesso direto a recursos.
  • Autenticação de múltiplos fatores (MFA) exige fatores de CATEGORIAS diferentes — duas senhas não é MFA.

12. Questões Estilo Banca (FGV / Cesgranrio / AOCP) — com Gabarito Comentado

1. O OAuth 2.0 é corretamente descrito como um:
  • (A) Protocolo de autenticação de usuários.
  • (B) Framework de autorização que permite acesso delegado a recursos, sem compartilhamento de senha.
  • (C) Protocolo de criptografia em trânsito equivalente ao TLS.
  • (D) Modelo de controle de acesso baseado em papéis (RBAC).
  • (E) Formato de certificado digital X.509.
Gabarito: B
Comentário: OAuth 2.0 (RFC 6749) é um framework de autorização — permite que uma aplicação acesse recursos em nome do usuário sem obter sua senha. Autenticação de identidade é papel do OpenID Connect, construído sobre o OAuth2.
2. Assinale a alternativa que apresenta o elemento responsável por adicionar uma camada de autenticação (identidade do usuário) ao OAuth 2.0:
  • (A) SAML 2.0.
  • (B) Refresh Token.
  • (C) OpenID Connect (OIDC), por meio do ID Token.
  • (D) TLS 1.3.
  • (E) PKCE.
Gabarito: C
Comentário: O OpenID Connect é uma camada de identidade construída sobre o OAuth 2.0, introduzindo o ID Token (formato JWT) com informações (claims) sobre a identidade autenticada do usuário.
3. Em relação às versões do protocolo SSL/TLS, é correto afirmar que:
  • (A) O SSL 3.0 é a versão mais recente e recomendada atualmente.
  • (B) O SSL 3.0 foi formalmente depreciado pela RFC 7568, sendo o TLS 1.3 a versão mais atual e recomendada.
  • (C) TLS e SSL são nomes diferentes para exatamente o mesmo protocolo, sem diferenças técnicas.
  • (D) O TLS 1.3 aumentou o número de round trips do handshake em relação ao TLS 1.2.
  • (E) O TLS não utiliza criptografia simétrica em nenhuma etapa da comunicação.
Gabarito: B
Comentário: A RFC 7568 (2015) depreciou formalmente o SSL 3.0 devido à vulnerabilidade POODLE. O TLS 1.3 (RFC 8446) é a versão mais atual, reduzindo (e não aumentando) o número de round trips do handshake para 1 RTT.
4. O modelo de controle de acesso em que o próprio proprietário do recurso decide, a seu critério, quem pode acessá-lo (tipicamente via listas de controle de acesso) é denominado:
  • (A) MAC — Mandatory Access Control.
  • (B) DAC — Discretionary Access Control.
  • (C) RBAC — Role-Based Access Control.
  • (D) ABAC — Attribute-Based Access Control.
  • (E) SSO — Single Sign-On.
Gabarito: B
Comentário: DAC (Discretionary Access Control) é o modelo em que o dono do recurso concede/revoga acessos a seu critério, geralmente por meio de ACLs. MAC é o oposto — controle centralizado e mandatório por rótulos de classificação.
5. O modelo formal Bell-LaPadula, aplicado a sistemas com controle de acesso obrigatório (MAC), tem como foco principal:
  • (A) Integridade dos dados, impedindo escrita em níveis superiores.
  • (B) Confidencialidade dos dados, impedindo leitura em níveis superiores ("no read up") e escrita em níveis inferiores ("no write down").
  • (C) Disponibilidade dos serviços em ambientes de alta criticidade.
  • (D) Autenticação multifator de usuários privilegiados.
  • (E) Auditoria e não-repúdio de transações financeiras.
Gabarito: B
Comentário: Bell-LaPadula é voltado à confidencialidade, com as regras "no read up" (simple security property) e "no write down" (star property). O modelo Biba, com regras opostas, é que trata de integridade.
6. No protocolo SAML 2.0, o documento XML assinado digitalmente, emitido pelo Identity Provider (IdP) e enviado ao Service Provider (SP) para comprovar a autenticação do usuário, é denominado:
  • (A) Access Token.
  • (B) ID Token.
  • (C) SAML Assertion.
  • (D) Refresh Token.
  • (E) Client Credential.
Gabarito: C
Comentário: A SAML Assertion é o artefato XML assinado que carrega as afirmações sobre a autenticação/atributos do usuário, entregue do IdP ao SP para conceder acesso. Os demais termos (Access Token, ID Token, Refresh Token, Client Credential) pertencem ao vocabulário OAuth2/OIDC, não ao SAML.
7. Sobre a porta padrão e a camada de segurança utilizada pelo protocolo HTTPS, é correto afirmar que:
  • (A) Utiliza a porta 80, com criptografia via IPSec.
  • (B) Utiliza a porta 443, com o tráfego protegido por TLS.
  • (C) Utiliza a porta 8080, sem qualquer camada de criptografia.
  • (D) Utiliza a porta 443, mas sem qualquer verificação de identidade do servidor.
  • (E) Utiliza a porta 22, protegida por SSH.
Gabarito: B
Comentário: HTTPS utiliza por padrão a porta 443 e protege a comunicação por meio do protocolo TLS (sucessor do SSL), garantindo confidencialidade, integridade e autenticação do servidor (via certificado digital).
8. Qual dos seguintes fluxos (grant types) do OAuth 2.0 é o mais recomendado atualmente para aplicações de página única (SPA) e aplicativos móveis, que não conseguem armazenar um segredo de cliente com segurança?
  • (A) Client Credentials.
  • (B) Implicit Grant.
  • (C) Authorization Code com PKCE.
  • (D) Resource Owner Password Credentials.
  • (E) Device Code.
Gabarito: C
Comentário: O fluxo Authorization Code combinado com PKCE (Proof Key for Code Exchange) é a recomendação atual para clientes públicos (SPAs e apps móveis), substituindo o Implicit Grant, hoje desaconselhado por razões de segurança.
9. A propriedade de segurança que garante que a captura futura da chave privada de longo prazo de um servidor NÃO permite descriptografar sessões TLS passadas, tornada obrigatória no TLS 1.3, é denominada:
  • (A) Non-repudiation (não repúdio).
  • (B) Mutual authentication (autenticação mútua).
  • (C) Forward secrecy (sigilo futuro/perfeito).
  • (D) Data masking (mascaramento de dados).
  • (E) Session fixation protection.
Gabarito: C
Comentário: Forward secrecy é garantida pelo uso de chaves efêmeras (Diffie-Hellman/ECDHE) a cada sessão. O TLS 1.3 tornou essa propriedade obrigatória ao remover a troca de chaves RSA estática, presente ainda como opção no TLS 1.2.
10. Considerando a diferença entre os tokens emitidos em um fluxo OpenID Connect, é correto afirmar que:
  • (A) O Access Token e o ID Token são exatamente o mesmo artefato, apenas com nomes diferentes.
  • (B) O Refresh Token é usado diretamente para acessar recursos protegidos na API.
  • (C) O ID Token, no formato JWT, carrega informações de identidade do usuário autenticado, enquanto o Access Token concede acesso a recursos protegidos.
  • (D) O Access Token é sempre um documento XML assinado.
  • (E) O ID Token substitui integralmente a necessidade de HTTPS na comunicação.
Gabarito: C
Comentário: No OpenID Connect, o ID Token (JWT) carrega claims de identidade do usuário, enquanto o Access Token (herdado do OAuth2) é usado para autorizar chamadas ao Resource Server. O Refresh Token apenas renova o Access Token, não acessa recursos diretamente. Nada dispensa o uso de TLS/HTTPS para proteger o transporte desses tokens.
